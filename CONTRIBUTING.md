# Contributing to dagger

Thanks for your interest in this project. `dagger` is an active research codebase
built phase-by-phase (see [`CLAUDE.md`](CLAUDE.md), the single source of truth for
the project's plan, math, and guardrails) — please read its §1 and §5 before
proposing a change; most contribution questions are answered there.

## The one rule

Every speaker's output waveform must be computed from the untouched overlap
mixture `x_O` -- never from a running residual (`CLAUDE.md` §1). This is enforced
structurally (`dagger/audio/provenance.py`'s `TrackedSignal`, the `Extractor` ABC's
guard) and by a dedicated test, `tests/test_no_residual_in_audio_path.py`. If your
change touches `dagger/extract/`, `dagger/reconstruct/`, `dagger/refine/`, or
`dagger/audio/provenance.py`, run that file explicitly and make sure it still
passes:

```bash
pytest tests/test_no_residual_in_audio_path.py -v
```

## Development setup

```bash
git clone https://github.com/RohanBanerjee88/dagger.git
cd dagger
pip install -e '.[dev]'      # numpy, pyyaml, pytest
pytest                        # should be green: numpy/torch-CPU only, no GPU or corpus needed
```

Optional extras depending on what you're touching:

- `.[data]` — real-corpus loaders (LibriMix / WSJ0-2mix): adds `soundfile`,
  `scipy`, `python-dotenv`.
- `.[ml]` — the learning stack (`torch`, `torchaudio`, `transformers`,
  `nemo_toolkit[asr]`): needed for the speaker encoder and training/eval scripts.
- `.[viz]` — `matplotlib`, only needed for `scripts/plot_phase2_depth.py`.

Torch-dependent tests (`tests/phase1/`) skip cleanly if `torch` isn't installed, so
`.[dev]` alone is enough to run most of the suite.

## Code conventions

- **Type hints + `from __future__ import annotations`** throughout; match the
  existing style rather than introducing a new one.
- **Every module, class, and function gets a docstring.** The current house style
  is a concise prose summary (parameters are covered by type hints, not separate
  `Args:`/`Returns:` blocks) — a more formal docstring convention (Google or NumPy
  style) is on the roadmap but not yet adopted; don't reformat existing docstrings
  as a side effect of an unrelated change.
- No formatter/linter is enforced yet (`black`/`ruff` + CI lint step is on the
  roadmap) — keep changes consistent with surrounding code in the meantime.
- New functionality should ship with unit tests. Look at `tests/phase0/` and
  `tests/phase1/` for the existing pattern (class-per-module-under-test,
  synthetic fixtures via `tests/conftest.py` — no real corpus or GPU required for
  the core suite).

## One phase at a time

`CLAUDE.md` §5 lays out the project in phases (0 through 4), each with an explicit
"Definition of Done." Don't start Phase *N+1* work in a PR until Phase *N*'s DoD is
green, and say in your PR description which phase/module the change targets. If
you're fixing a bug in an earlier phase (e.g. Phase 0/1) while later-phase work is
in progress, that's fine — just don't mix phase-advancing work with unrelated
fixes in the same PR.

## Commit / PR discipline

- Small commits per module; tests green before merge.
- Reproducibility matters here: any new experimental result should come from a
  `scripts/run_phaseN.py` (or `train_phaseN.py`) run against a checked-in
  `configs/*.yaml` — no numbers that can't be regenerated by one command.
- If your change affects a claim in `README.md`'s Results/Limitations sections or
  in `CLAUDE.md`, update that documentation in the same PR.

## Reporting issues

Open a GitHub issue. If it's about a specific experimental result, include the
config file and command used, and whether you ran with oracle or real diarization.
